## 先說重點

績效系統難的從來不是把表格畫出來，是這三件事：

| 難題 | 這套 Demo 怎麼處理 |
|---|---|
| **誰能看到誰的分數？** | 三級權限。員工只看得到自己，主管看部門，管理員看全部。而且**員工在定版前看不到主管給的分數** |
| **評核要經過哪些關卡才算數？** | 五狀態流程：自評 → 主管評核 → 複核 → 定版，定版後可申訴退回。每一步都寫進稽核軌跡 |
| **兩個人同時改同一筆怎麼辦？** | 存檔前比對版本號。別人先改過就中止存檔、跳衝突，讓你選「載入對方版本」或「以我的覆蓋」 |

這三件事在純靜態網頁上實作的方式：身分存 **sessionStorage**（所以同一個瀏覽器的不同分頁可以是不同人），共用資料存 **localStorage** 當伺服器，跨分頁用 **BroadcastChannel** 即時同步。

| 模組 | 內容 |
|---|---|
| **營運總覽** | 依身分顯示不同內容：主管以上看公司營收、評核進度、庫存；一般員工看自己的業績與評核狀態 |

## 績效制度的設計

### 兩套評核模板

如果全公司用同一張評分表，製茶師和會計永遠贏不過業務 —— 他們根本沒有業績數字。所以分成兩套：

| 業務型（批發／門市／電商／企業客製） | 權重 | | 職能型（茶廠製茶／品管／行政） | 權重 |
|---|---|---|---|---|
| 業績達成率 | 40% | | 工作產出 | 40% |
| 毛利貢獻 | 25% | | 品質穩定 | 25% |
| 新客開發 | 15% | | 流程改善 | 15% |
| 客戶滿意 | 10% | | 跨部門協作 | 10% |
| 出勤紀律 | 10% | | 出勤紀律 | 10% |

加權總分 = Σ（各項分數 × 權重）÷ 100，單項上限 130 分（超標可加分）。
等第：**A** ≥ 90、**B** ≥ 80、**C** ≥ 70、**D** < 70。

示範資料的分布是 2A / 3B / 2C / 1D —— 刻意不做成全員 A，因為一套每個人都拿 A 的績效制度沒有意義。

### 評核流程

```
待自評 ──送出自評──▶ 主管評核中 ──送出評核──▶ 複核中 ──定版──▶ 已定版
                          ▲                      │              │
                          └──────退回主管─────────┘              │
                          ▲                                     │
                          └──────受理並重評──── 申訴中 ◀──申訴────┘
```

動作的權限綁在狀態機上，不是靠畫面藏按鈕：

| 動作 | 從 → 到 | 誰能做 |
|---|---|---|
| 送出自評 | 待自評 → 主管評核中 | 本人 |
| 代為跳過自評 | 待自評 → 主管評核中 | 管理員（避免有人不自評就把整個週期卡死） |
| 送出評核 | 主管評核中 → 複核中 | 直屬主管 / 管理員 |
| 定版 | 複核中 → 已定版 | 管理員 |
| 退回主管 | 複核中 → 主管評核中 | 管理員（**必填複核意見**） |
| 提出申訴 | 已定版 → 申訴中 | 本人（**必填申訴理由**） |
| 受理並重評 | 申訴中 → 主管評核中 | 直屬主管 / 管理員 |

幾個刻意做進去的規則：

- **沒有人可以評自己。** 主管本人的評核由管理員處理 —— 程式層面直接排除，不是靠提醒。
- **員工在定版前看不到主管分數**，避免流程中途互相影響。定版或進入申訴後才公開。
- **管理員可以開啟新週期**，全員重設為待自評，上期分數封存進稽核軌跡（兩段式確認，不會手滑）。

## 技術決策

這些選擇都是為了「交付給非技術人員也能用」：

- **零相依、零建置步驟。** 沒有 npm、沒有打包工具，就 4 個檔案。
- **連 `file://` 都能跑。** 刻意不用 ES module（會被 CORS 擋），改用傳統 script。下載 ZIP 解壓後點兩下 `index.html` 就能開。
- **身分放 sessionStorage、資料放 localStorage。** 這個拆法讓同一個瀏覽器的不同分頁可以是不同使用者，多人情境才演得出來。
- **樂觀鎖（optimistic locking）。** 每筆評核帶版本號，存檔前重讀共用資料比對；不一致就中止並跳衝突，而不是硬蓋。這跟真的後端做法是同一套，只是把 DB 換成 localStorage。
- **所有 storage 存取都包 try/catch。** 無痕模式或封鎖 storage 時自動降級成唯讀瀏覽，不會白畫面。
- **BroadcastChannel 做跨分頁同步與線上名單**，不支援的瀏覽器退回 `storage` 事件。
- **統計數字全部即時計算**，不是寫死的假數字。
- **手刻 SVG 圖表**，不載任何圖表函式庫。
- **深／淺色主題**：跟隨系統設定，也可手動切換，選擇會被記住。響應式，手機可用。

### 無障礙與配色

- 配色跑過色盲模擬與對比度驗證。淺色模式下部分色階低於 3:1，所以每張圖都附**直接數值標籤**與**表格檢視**切換 —— 資訊不會只靠顏色傳達。
- 狀態一律「顏色 + 文字」成對出現（例如「● 急需補貨」），不是只給一個紅點。
- 表格可用鍵盤 Tab / Enter 操作，折線圖可用左右方向鍵逐月查看。

### 測試

用 jsdom 寫了 **78 項煙霧測試**，涵蓋登入閘門、三種身分的可見範圍、完整評核流程、退回必填驗證、版本衝突的偵測／載入／覆蓋三條路徑、申訴、稽核軌跡、週期重設、跨分頁同步、權限過濾套用到 CSV 匯出、主題切換。對本機與正式網址各跑一次，全數通過。

寫測試的過程中抓到一個真的設計漏洞：原本員工不送自評，管理員沒有任何方法推進流程，整個週期會卡死。所以補了「代為跳過自評」。

## 這套 Demo 還沒做的事

為了誠實起見，列出刻意跳過的部分 —— 這些才是真正上線前要處理的：

- **沒有後端與資料庫。** 資料存在瀏覽器，換台電腦就沒了。真系統要 DB、備份、還原。
- **沒有真的身分驗證。** 登入是直接選身分，沒有密碼、沒有 SSO、沒有 session 過期。權限模型是真的，驗證不是。
- **沒有與現有系統介接。** 公司既有的進銷存或會計軟體要怎麼對帳，是另一個題目。
- **沒有通知。** 真流程需要「輪到你自評了」的信件或 LINE 通知，否則沒人會記得。
- **衝突處理只做到整筆層級**，沒有做到欄位級的合併。

以每天 4 小時計，把這些補到可上線，估計 2 到 4 個月。
